SYSELL Web — Estándares de Arquitectura y Desarrollo 
1. OBJETO 
Establecer el estándar de arquitectura y desarrollo del sistema SYSELL como sistema web, definiendo 
los lineamientos, patrones y buenas prácticas de arquitectura, codificación, base de datos, seguridad 
e interfaz que garanticen uniformidad, mantenibilidad, seguridad y calidad. El documento fusiona los 
estándares institucionales entregados por el docente (Anexo 9-29 MCVS-604, Manual SYAR, 
Estándares de Desarrollo de BD y Guías UNJBG 2026), sustituyendo el patrón MVC/BFF por Clean 
Architecture + CQRS, y los adecúa al proyecto SYSELL de Comercial Machi's. 
2. FINALIDAD 
Uniformizar el desarrollo de SYSELL como aplicación web accesible desde cualquier dispositivo con 
navegador, manteniendo la lógica de negocio centralizada en el backend. Cualquier integrante del 
equipo debe poder comprender y extender el código sin ambigüedad sobre la organización de capas, 
la nomenclatura o el flujo de datos. 
3. ÁMBITO DE APLICACIÓN 
El estándar es de aplicación obligatoria para todos los componentes del sistema web SYSELL 
desarrollados por Pollitos Design: el cliente web responsive (Administrador y Vendedor), la API REST 
y la base de datos MySQL. 
Permanecen fuera del alcance: pasarela de pago en línea, integración con SUNAT y comprobantes 
electrónicos, módulo de compras a proveedores y tienda virtual para clientes externos. 
4. MARCO METODOLÓGICO Y REFERENCIAS 
4.1. Clean Architecture 
Organiza el software en capas concéntricas (Dominio, Aplicación, Infraestructura y Presentación) con 
la Regla de Dependencia: las capas internas nunca dependen de las externas. Así, las reglas de 
negocio de SYSELL (control de stock, ganancias, roles) no dependen del navegador, del framework ni 
de la base de datos. 
4.2. CQRS 
Separa las operaciones que modifican el estado (Commands, por ejemplo registrar una venta) de las 
que solo consultan (Queries, por ejemplo consultar stock o un reporte). En el frontend web se refleja 
como consultas y mutaciones independientes. 
4.3. API-first 
El backend se diseña como una API REST independiente de la interfaz. El cliente web consume los 
endpoints de la API y toda la regla de negocio reside en el backend. 
4.4. ISO/IEC 25010 y DevSecOps 
La calidad se evalúa con los ocho atributos de ISO/IEC 25010 definidos en el Informe de Producto 
Final, y la seguridad se incorpora desde el diseño (Shift Left), atendiendo las observaciones de las 
auditorías internas y externas del equipo.

7. PATRÓN CQRS 
7.1. Principios 
●​ Un Command modifica el estado, se nombra en imperativo y devuelve a lo sumo un 
identificador. 
●​ Una Query solo lee y devuelve DTOs de lectura optimizados; nunca modifica datos. 
●​ Cada Command o Query tiene exactamente un Handler. 
●​ En el frontend, las Queries se implementan como consultas con caché (GET) y los Commands 
como mutaciones (POST, PUT, DELETE) que invalidan la caché afectada.

7.3. Flujo de un Command web: Realizar venta (CU.2) 
●​ 1. En VentaPage el vendedor confirma la venta; el hook useRegistrarVenta envía POST 
/api/v1/ventas. 
●​ 2. VentaController valida la entrada y crea RegistrarSalidaProductoCommand. 
●​ 3. El CommandBus lo entrega a RegistrarSalidaProductoHandler. 
●​ 4. El Handler verifica stock (regla de Dominio), crea la Venta, descuenta stock y registra 
método de pago y ganancia en una sola transacción. 
●​ 5. Se responde 201 Created; el frontend invalida la caché de stock y ventas recientes. 
7.4. Flujo de una Query web: Consultar disponibilidad (R-09) 
●​ 1. El vendedor escribe en el buscador; useStockProducto envía GET 
/api/v1/productos/{id}/stock. 
●​ 2. El controller crea ConsultarDisponibilidadQuery y la envía al QueryBus. 
●​ 3. El QueryHandler lee de la BD y devuelve un DTO (nombre, talla, color, stock, precio) con 
200 OK.

●​ La API es el contrato único entre el cliente web y el backend; toda regla de negocio se 
resuelve en el servidor.

actualiza el contrato. 
●​ Versionado en la URL (/api/v1); los cambios que rompen compatibilidad crean /api/v2. 
●​ Listados con paginación (page, per_page) y filtros por query string.

14. CONTROL DE VERSIONES, CI/CD Y DESPLIEGUE 
●​ Ramas: main (producción), develop (integración), feature/<modulo>-<descripcion>, 
fix/<descripcion>, release/<version>. 
●​ Commits: Conventional Commits en español, ej.: feat(venta): registrar salida de producto con 
descuento de stock. 
●​ Pull Requests: obligatorios hacia develop, con al menos una revisión cruzada de otro 
integrante. 
●​ Integración continua: cada PR ejecuta compilación, lint, pruebas y análisis estático 
(SonarQube o Codacy). 
●​ Entornos: local (Docker Compose), staging (réplica de producción con BD de prueba) y 
producción. 
●​ Despliegue: desde main tras pasar CI; el frontend se compila a archivos estáticos y el 
backend se despliega con migraciones automáticas versionadas. 
●​ Prohibido: push directo a main o develop y subir archivos .env, claves o binarios. 
●​ Roles del equipo: Líder (Johan Mamani), Diseñador (Luis Condori), Programador (Aron 
Cachicatari), Testeador (Alex Chata), Analista (Pierrette Chávez).
